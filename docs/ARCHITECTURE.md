# Architecture

## 1. Overview

Static site built by Astro 7 and deployed to GitHub Pages by GitHub Actions. Every route is pre-rendered HTML. JavaScript ships only for React islands that need it.

```
content/{locale}/projects|skills|experience|certifications.json ──► src/content.config.ts (collections, zod)
content/{locale}/site.json ──────────────────────────────────────► src/lib/content.ts (import + siteSchema.parse)
                                    │
                                    ▼
                  src/lib/content.ts getters ──► src/lib/derive.ts (counts, sorting)
                                    │
                                    ▼
   src/pages/[locale]/*.astro ──► layouts ──► patterns (.astro / React islands) ──► ui primitives
                                                │
tokens/*.tokens.json ──► Style Dictionary ──► src/styles/tokens.css ──► Tailwind @theme ──► all components
```

Rule of dependency: **pages → layouts → patterns → ui → tokens**. A layer imports only from layers to its right. **Only pages, layouts and `src/lib/` read content** (through the getters in `src/lib/content.ts`); patterns and ui receive data as props.

## 3. Content layer

`projects`, `skills`, `experience` and `certifications` are Astro content collections loaded with the `file()` loader (each file is an array of objects with an `id`). `site.json` is a single object, so it is **not** a collection: `src/lib/content.ts` imports it and parses it with `siteSchema`. **Any schema error fails the build.** `npm run validate:content` runs `astro sync` (collections) plus `tests/unit/content.test.ts` is part of `npm test` (site schema + cross-file checks).

> Zod: in Astro 7 import it from `astro/zod` (`import { z } from 'astro/zod'`). Check the Astro 7 content-collections docs when implementing and follow them if the import path differs.

### 3.1 Schemas — `src/lib/schemas.ts` (implement exactly)

```ts
import { z } from 'astro/zod';

export const id = z.string().regex(/^[a-z0-9-]+$/);
export const todo = z.array(z.string()).default([]); // never rendered

export const image = z.object({
  src: z.string(),
  alt: z.string().min(5),
  caption: z.string().optional(),
  approved: z.boolean().default(false),
});

export const skillGroup = z.enum([
  'clouds',
  'development',
  'integration',
  'devops',
  'data',
  'delivery',
  'products',
  'tools',
  'languages-programming',
]);

export const skillSchema = z.object({
  id,
  label: z.string(),
  group: skillGroup,
  accent: z
    .string()
    .regex(/^cloud-[a-z]+$/)
    .optional(), // clouds only → var(--pf-g-color-{accent})
  aliases: z.array(z.string()).optional(),
});

const section = z.discriminatedUnion('type', [
  z.object({ type: z.literal('challenge'), body: z.string() }),
  z.object({
    type: z.literal('architecture'),
    body: z.string().optional(),
    image: image.optional(),
  }),
  z.object({
    type: z.literal('decisions'),
    items: z
      .array(
        z.object({
          decision: z.string(),
          why: z.string(),
          tradeoff: z.string().optional(),
        }),
      )
      .min(1)
      .max(4),
  }),
  z.object({ type: z.literal('gallery'), images: z.array(image) }),
  z.object({
    type: z.literal('outcomes'),
    items: z.array(
      z.object({
        label: z.string(),
        value: z.string().optional(),
        measured: z.boolean().default(false),
      }),
    ),
  }),
  z.object({ type: z.literal('takeaway'), body: z.string() }),
]);

export const projectSchema = z.object({
  id,
  title: z.string(),
  subtitle: z.string(),
  client: z.string(),
  employers: z.array(id).min(1), // experience ids; projects carry NO dates of their own
  role: z.string(),
  teamSize: z.string().optional(),
  industry: z.string().optional(),
  clouds: z.array(id).min(1),
  capabilities: z.array(id),
  category: z.string(),
  featured: z.boolean().default(false),
  depth: z.enum(['case-study', 'card']),
  summary: z.string().max(220),
  cover: z.object({
    preset: z.enum(['aurora', 'indigo', 'violet-edge', 'solid-blue']),
    image: image.optional(),
  }),
  sections: z.array(section).default([]),
  todo,
});

export const experienceSchema = z.object({
  // companies delivered through; NO dates
  id,
  employer: z.string(),
  role: z.string(),
  projectIds: z.array(id).default([]),
});

export const certificationSchema = z.object({
  id,
  label: z.string(),
  skills: z.array(id), // no dates
});

const seoPage = z.object({ title: z.string(), description: z.string() });

export const siteSchema = z.object({
  name: z.string(),
  role: z.string(),
  location: z.string(),
  headline: z.string(), // one-line claim under the role
  intro: z.string(), // **term** = brighter highlight
  bio: z.array(z.string()).min(1),
  principles: z.array(z.object({ title: z.string(), body: z.string() })),
  workIntro: z.string(),
  ctaLine: z.string(),
  workFacets: z.object({ clouds: z.string(), capabilities: z.array(id) }),
  skillGroups: z.array(z.object({ id: skillGroup, label: z.string() })),
  notFound: z.object({ title: z.string(), body: z.string() }),
  languages: z.array(z.object({ label: z.string(), level: z.string() })),
  links: z.object({
    email: z.string().email(),
    linkedin: z.string().url(),
    github: z.string().url(),
    resume: z.string().url(),
    credentials: z.union([z.string().url(), z.literal('')]),
  }),
  contact: z.object({
    intro: z.string(),
    projectTypes: z.array(z.string()).min(1),
    successMessage: z.string(),
    errorMessage: z.string(),
  }),
  seo: z.object({
    homeTitle: z.string(),
    description: z.string(),
    pages: z.object({
      work: seoPage,
      skills: seoPage,
      about: seoPage,
      contact: seoPage,
      notFound: seoPage,
    }),
  }),
  photo: image.nullable().default(null),
  todo,
});
```

`src/content.config.ts` defines one collection per type and locale (`projects-en`, `projects-pt`, …) with `file('content/{locale}/{name}.json')` and the shared schema. Every getter in `src/lib/content.ts` takes the page's locale.

Locales (`src/lib/i18n.ts`): pages read `strings(locale)` for UI text and build links with `localePath(locale, path)`; components without the route param use `localeFromPath(Astro.url.pathname)`. React islands receive their strings as props. A locale is built in production only when `src/i18n/locales.json` marks it `reviewed`. `tests/unit/i18n.test.ts` fails when UI keys or content ids differ between locales.

Cross-file integrity (checked in `tests/unit/content.test.ts`):

- every project `clouds[]` / `capabilities[]` id exists in `skills.json`; every `clouds[]` id has `group: "clouds"`;
- every id in a project's `employers` exists in `experience.json`, and each of those experiences lists the project in `projectIds` (and vice versa);
- every certification `skills[]` id and every `site.workFacets.capabilities` id exists in `skills.json`;
- every `site.skillGroups[].id` is a group used by at least one skill;
- at most 4 projects with `featured: true`; ids unique.

**No dates anywhere.** The site is a project showcase; career dates live on the resume. Content has no date fields, and no component renders dates (except the footer copyright year).

All pure functions, 100% line coverage.

### 3.3 Rendering rules that depend on data

- Outcomes: always render `label`; render `value` only when `measured: true`. Labels must read as complete statements on their own.
- Images (gallery, cover image, photo): render only when `approved: true` **and** the file exists in `public/` (`publicFileExists`, checked at build), so content can approve images before P1-08 ships the files. A cover image is used only when declared in `cover.image`; otherwise the gradient preset shows.
- `todo` fields: never rendered. In `astro dev` only, `BaseLayout` logs the count of open todos to the console.

### 4.3 Dev component gallery

`src/dev/components.astro` lives outside `src/pages/`, so production builds never see it. A small inline integration in `astro.config.mjs` injects it only for the dev server:

```js
const devGallery = () => ({
  name: 'dev-gallery',
  hooks: {
    'astro:config:setup': ({ command, injectRoute }) => {
      if (command === 'dev')
        injectRoute({ pattern: '/dev/components', entrypoint: './src/dev/components.astro' });
    },
  },
});
```

It is therefore never built, never deployed and never in the sitemap. The same integration injects `/dev/og/[...route]` (`src/dev/og.astro`): one 1200×630 social card per route, which `npm run og` (`scripts/og.mjs`) screenshots into `public/og/` (P3-05); a locale prefix (`/dev/og/pt/work`) renders the translated card into `public/og/{locale}/`, for reviewed languages only (`--drafts` for a local preview). The route is a path segment, not a query, because prerendered pages get no search params even in dev.

## 5. Styling

- `global.css`: `@import "tailwindcss"; @import "./tokens.css"; @import "./covers.css";` then `@theme` maps Tailwind names to tokens, e.g. `--color-surface-1: var(--pf-g-color-surface-1);`, `--font-heading: var(--pf-g-font-family-heading);`, `--radius-lg: var(--pf-g-radius-lg);`. Breakpoints in `@theme` are literal (`--breakpoint-lg: 1024px;` …) because media queries cannot use `var()`.
- Components use those Tailwind names (`bg-surface-2 text-on-surface-1 rounded-lg`). No arbitrary values (`bg-[#123]`).
- shadcn components: after `shadcn add`, replace their default CSS variables with token-mapped ones in `global.css`; do not keep shadcn's default palette.
- After `shadcn add`: import `cn` from `@/lib/utils` (the CLI writes `from "cn"`), and replace default Tailwind names the theme clears (`text-sm`, `rounded-xl`, `shadow-lg`, `ring-*` focus styles) with token names.

## 6. Theme

Inline script in `BaseLayout` `<head>` (before CSS paints):

```html
<script is:inline>
  try {
    const s = localStorage.getItem('pf-theme');
    const t = s ?? (matchMedia('(prefers-color-scheme: light)').matches ? 'light' : 'dark');
    document.documentElement.dataset.theme = t;
  } catch {
    document.documentElement.dataset.theme = 'dark';
  }
</script>
```

3D scenes read colours with `getComputedStyle(document.documentElement)` and re-read them on the `pf-themechange` event dispatched by `ThemeToggle`.

## 8. CI/CD and repository files

### 8.1 Scripts (`package.json`)

```json
{
  "predev": "npm run tokens",
  "dev": "astro dev",
  "tokens": "node style-dictionary.config.js",
  "build": "npm run tokens && astro check && astro build",
  "preview": "astro preview",
  "lint": "eslint . && prettier --check .",
  "test": "vitest run",
  "test:a11y": "playwright test",
  "og": "node scripts/og.mjs",
  "validate:content": "astro sync",
  "check:links": "linkinator dist --recurse --skip \"^(?!http://(localhost|127\\.0\\.0\\.1)[:/])\"",
  "ci": "npm run tokens && npm run lint && npm run validate:content && npm test && npm run build && npm run check:links",
  "prepare": "husky"
}
```

`ci` generates the tokens first: `tokens.css` is git-ignored, and lint needs it because the Prettier Tailwind plugin reads `global.css`, which imports it (a clean CI checkout failed without it). `tokens` runs `style-dictionary.config.js` as a Node script (Style Dictionary API, two runs: `:root` and `[data-theme="light"]` share token paths, so one CLI build cannot emit both). `test:a11y` (`playwright test`, P3-04) runs against the built `dist/` through `astro preview` on port 4322, in the second workflow (§8.5), not in `ci`; run `npm run build` first. The `check:links` skip pattern checks internal links only; external links are checked manually before launch. Linkinator 8 serves `dist/` on `127.0.0.1`, so a `localhost`-only pattern skips every link and the check passes vacuously; if "Scanned 0 links" ever appears, the pattern is wrong.

```yaml
    if: github.ref == 'refs/heads/main' && github.event_name != 'pull_request'
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@v5
```

Repository settings: Pages → Source = GitHub Actions; repository **variable** (not secret) `PUBLIC_WEB3FORMS_KEY`; branch protection on `main` requiring the `build` job and the two `quality.yml` jobs (`E2E and accessibility`, `Lighthouse`).

### 8.5 `.github/workflows/quality.yml`

Runs on pull requests (and manually). Two jobs, each `npm ci` + `npm run build` on Node from `.nvmrc`:

- **E2E and accessibility:** `npx playwright install --with-deps chromium`, then `npm run test:a11y`. `playwright.config.ts` runs `tests/e2e/` at 1440px and 375px. `smoke.spec.ts` checks every sitemap route (200, one `h1`, no console errors), the 404 page (status 404, `noindex`) and the nav (desktop rail and mobile sheet). `a11y.spec.ts` runs axe (WCAG 2.2 AA + best practices) on every route and the 404 page in both themes, with reveal sections shown. Report uploaded on failure.
- **Lighthouse:** `npx -y @lhci/cli@0.15.1 autorun` with `lighthouserc.json`: `dist/` served statically; Home, `/work/` and `/work/brf/`; mobile profile, 3 runs; every category ≥ 0.95 (performance by median). Reports uploaded as an artifact. `@lhci/cli` is not a devDependency: its dependency tree (puppeteer, `tmp`, `uuid`, `basic-ftp`) carries `npm audit` advisories and it has had no release since 2025-06, so it runs pinned through `npx` and stays out of the lockfile.

Merges are blocked only when branch protection lists both jobs as required checks (§8.2).

## 10. Error handling

- Missing optional content → section not rendered.
- Missing required content → build fails (zod).
- WebGL context lost / unavailable → swap to fallback, no error UI.
- Contact form network error → inline error with retry; never lose typed text.
- `PUBLIC_WEB3FORMS_KEY` empty → contact form not rendered; email and LinkedIn links remain.
